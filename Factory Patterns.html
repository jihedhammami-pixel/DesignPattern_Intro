Factory Method
& Abstract Factory

Every new in your code is a decision about which class to use. This chapter shows you how to move that decision to one place, so the rest of your program can grow without being rewritten.

Step 1 · The problem

Why new becomes a problem

what coupling to a concrete class meanswhy change requests hurtthe idea of "who decides"

Imagine an online shop that notifies customers when an order ships. The first version only sends emails, so the developer writes new EmailSender() directly in the order code. It works. Then the business asks for SMS. Then push notifications. Each time, someone opens the order code and adds another if.

The real problem isn't the new keyword itself. The code that uses a notification also decides which class to create. Those are two different jobs, and they change for different reasons.

Analogy · the restaurant

You order from the menu. You don't walk into the kitchen.

As a customer you ask for "today's soup". You don't choose the pot, the stove or the cook. The kitchen decides how the soup is made, and it can change its recipe tomorrow without telling you.

Customer→the code that uses an objectMenu item→an interface, like ChannelKitchen→the factory, which decides and creates

From practice

On large projects, these scattered if/else chains are where bugs hide. Someone adds the new case in three places and forgets the fourth, and nobody notices until a customer in that one flow gets nothing. The goal of every factory pattern is to make the "which class?" decision in one place.

Step 2 · A first step

The simple factory

moving creation into one classcoding to an interfaceits limit

The obvious first fix is to put all the new calls in one class. Every other class asks it for a Channel and never names EmailChannel or SmsChannel. This is often called a simple factory.

✓What we gained

The order, invoice and reminder code only know the Channel interface. The "which class?" decision lives in one switch.

✗What is still wrong

Every new channel still means editing ChannelFactory. The class is never closed for modification, and every team edits the same file.

i

Vocabulary check

The simple factory is a useful idiom, not one of the 23 patterns in the Gang of Four book (Gamma, Helm, Johnson and Vlissides, 1994). It's the stepping stone. The two real patterns in this chapter fix its limit in two different ways: Factory Method uses inheritance, and Abstract Factory uses an object you pass in.

Step 3 · The first pattern

Factory Method

the intentthe four rolesbuilding it in 5 stepswatching it run
≡

Intent, in plain words

A base class declares a method that creates an object. Subclasses decide which concrete class that method returns.

The base class runs the business logic and calls the method whenever it needs the object. It never writes new for a concrete product.

Analogy · the coffee chain

Head office writes the routine. Each branch picks its machine.

A coffee chain's head office writes one routine for every branch: take the order, make the drink, serve, and record the sale. It leaves one step open: which machine makes the drink. The Rome branch uses an espresso machine, the Kyoto branch a matcha whisk, and the London branch a filter brewer.

The routine never changes when a new branch opens. The new branch only answers one question: "what machine do you use?"

Head office routine→the Creator with its business logic"make the drink" step→the factory methodEach branch→a Concrete CreatorEach machine→a Concrete Product

Notice that send() is a template: fixed steps with one variable step. Factory Method is often used inside a Template Method like this. When you read a framework and see an abstract or overridable create…() method called from inside a longer algorithm, you are looking at a Factory Method.

Step 4 · A new kind of problem

When objects come in families

what a product family iswhy mixing families is a bug

Factory Method creates one product. Some designs need several products that must match each other. A dashboard app with a Daylight theme and a Midnight theme is a good example. Each theme has its own button, checkbox and card. A Daylight button on a Midnight card isn't just ugly. It is a bug that users will report.

Analogy · the meal kit

Order one kit, and everything inside matches.

A meal-kit company sells a Japanese kit and an Italian kit. You never open the Italian box and find chopsticks and miso. You pick one kit, and the company guarantees that every item in it belongs together.

The kit box changes colour as a whole. That is the guarantee.

Key idea

A product family is a set of objects designed to be used together. The design must make it impossible to mix families by accident. Discipline and code reviews aren't enough. On side B, the mistake simply can't be written.

Step 5 · The second pattern

Abstract Factory

the intentthe structurebuilding it in 5 stepsits cost: the axis of change
≡

Intent, in plain words

One interface with a create method for each product in a family. Each implementation creates one complete, matching family.

The client receives a factory object and asks it for products. It never names a concrete class and can't mix families.

From practice

Abstract Factory makes adding a family cheap and adding a product type expensive. Before you choose it, ask the people who own the product: "Next year, will we add more themes, or more kinds of widgets?" If the honest answer is "more kinds of widgets", this pattern will fight you.

Step 7 · Field notes

In practice and in modern Java

where the JDK uses these patternslighter modern formscommon mistakes

You already use them

In the JDKPatternWhy it fits
Collection.iterator()Factory MethodArrayList and HashSet each return their own iterator class. You only see Iterator.
Connection.createStatement(), prepareStatement() (JDBC)Abstract FactoryA connection from the PostgreSQL driver creates a matching family of PostgreSQL statements. You never mix drivers.
DocumentBuilderFactory.newInstance()Abstract FactoryReturns a factory for the XML parser implementation available at runtime. Your code never names it.
List.of(), Integer.valueOf(), Optional.of()Static factory methodA static method that returns an instance. It's an idiom, not GoF's Factory Method, because there is no subclass overriding.

Lighter forms in modern Java

Since Java 8, a factory doesn't always need its own class hierarchy. When the only variation is "which constructor?", a function is enough.

A registry of constructors

Adding WhatsApp is one new line here and one new class. This is the usual way to remove the switch from the simple factory.

A Supplier passed in

Supplier<Channel> is a one-method factory interface. It is Factory Method without the subclass.

Mistakes to avoid

1A factory for one class

If there is one implementation and no real reason for a second, write new. Add the factory when the second variant appears.

2Leaking concrete types

A factory that returns EmailChannel instead of Channel gives the coupling straight back to the caller.

3Parallel hierarchies

With Factory Method, every new product often needs a new creator subclass. Watch for two hierarchies growing in lockstep; a registry or a Supplier may be simpler.

4Choosing the factory everywhere

Decide which concrete factory to use once, at startup in main (the "composition root"), then pass it in. Repeating that if around the code brings back step 1.

!

Naming conventions you will meet

createX() and newX() usually return a fresh object. of(), from() and valueOf() convert or wrap values. getInstance() may return a shared object, as in the Singleton lab. Reading names this way tells you a lot about an API before you open the docs.

Final checkpoint

Summary and final check

1The problem

  • Using an object and choosing its class are two jobs.
  • Put the choice in one place.

FMFactory Method

  • One product.
  • A subclass overrides createX().
  • Base class logic uses only the interface.

AFAbstract Factory

  • A family of matching products.
  • The client receives a factory object.
  • New family: cheap. New product: expensive.

★Rules of thumb

  • No second variant? Use new.
  • Choose the factory once, in main.
  • Return interfaces, never concrete types.
