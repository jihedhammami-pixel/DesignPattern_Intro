Why Object-Oriented Programming?

From functions that touch shared data to objects that talk to each other

In procedural code, data and the functions that change it live apart. As a program grows, any function can modify any data, and one bug can spread everywhere. Object-oriented programming groups data together with the code that is allowed to change it. Objects then cooperate by sending messages, which in Java means calling each other's methods.

🧩 Modularity

Each class is a self-contained unit you can understand, test and replace on its own.

♻️ Reuse

Inheritance and composition let you build new types from existing ones instead of copying code.

🔌 Extensibility

Polymorphism lets you add new types without editing the code that uses them.

🛡️ Safety

Encapsulation keeps objects in a valid state, because only their own methods can change them.

Class & Object

Blueprint versus the things built from it, and where they live in memory

A class is a blueprint. It declares state (fields) and behavior (methods). An object is one concrete instance of that class, created at run time with new. Every object has its own copy of the instance fields.

Anatomy of a class (UML)



  
Where do objects live? Stack and heap

  
Local variables live on the stack, inside the frame of the method that is running. Objects live on the heap. A variable of a class type never holds the object itself, only a reference (an arrow) to it. Step through the code to watch what happens.

Inside a Class: Constructors, this, static
The members that every class is built from

  

    
Constructor
Same name as the class, no return type. It runs once, when new creates the object. If you write none, Java adds a no-argument default constructor.

    
this
A reference to the current object. Use this.name = name when a parameter has the same name as a field, and this(…) to call another constructor of the same class.

    
static
Belongs to the class, not to any one object. A static field is shared by all instances. A static method has no this.

    
Overloading
Several methods or constructors with the same name but different parameters. The compiler picks one from the argument types.

  

  
  

  
Rule of thumb: if a value describes one object (a student's name), make it an instance field. If it describes the class as a whole (how many students exist), make it static.

Encapsulation
Hide the data, expose safe operations

  
Encapsulation bundles state with the methods that operate on it, and restricts direct access to that state. Fields are usually private, and outside code goes through public methods that check the rules. The class guards its own invariants (rules that must always be true, such as "balance is never negative").

Abstraction
Show what an object does, hide how

  
Abstraction exposes a simple contract and hides the implementation details. Callers depend on the contract, so implementations can change or be swapped freely. In Java, contracts are written with interfaces and abstract classes.

Inheritance
Reuse and specialise with extends ("is-a")

  
A subclass inherits the fields and methods of its superclass and can add new ones or override existing ones. Java allows only one direct superclass, and every class ultimately extends java.lang.Object. Use inheritance only when "B is a A" is really true.

  
  
Constructor chaining

  
Before a subclass initialises its own fields, its superclass part must be built. That is why each constructor calls super(…), explicitly or implicitly. Java 25 With flexible constructor bodies (JEP 513), you may now run statements before super(…), such as validating arguments, as long as they don't use the object under construction.

Overriding and super

  

  

    
Overriding rules
  • Same name and parameter list
  • Return type: same or a subtype (covariant)
  • Visibility: same or wider, never narrower
  • Cannot override private, static or final methods
  • Add @Override: the compiler then checks it for you

    
final stops inheritance
  • final class: cannot be extended (e.g. String)
  • final method: cannot be overridden
  • final field: assigned exactly once

Polymorphism
One reference type, many runtime behaviors

  
A variable of a supertype can refer to an object of any subtype. When you call an overridden method, Java picks the version from the actual object at run time. This is dynamic dispatch. Two rules to remember:

  

    
1 · The reference type decides what you may call
Checked by the compiler. With Animal a, you may only call methods that Animal declares.

    
2 · The object type decides which version runs
Decided at run time. If a refers to a Dog, a.sound() runs Dog's version.

Part III · Design




  
8
Relationships Between Classes
Reading and drawing UML connections

  
Classes rarely work alone. UML has a specific arrow for each kind of relationship. Learn to recognise them; they appear in every design document.

  
  
Composition over inheritance

  
Inheritance couples a subclass tightly to its parent and is fixed at compile time. Composition holds a part in a field, so the part can be replaced at run time. Prefer composition unless the "is-a" relationship is genuine.

  

  
Quick test: say the sentence out loud. "A car is an engine" sounds wrong, so use composition. "A dog is an animal" sounds right, so inheritance may fit.






  
9
The Object Contract: equals, hashCode, toString
Methods every class inherits, and when to override them

  

    
== compares references
True only when both variables point to the same object.

    
equals() compares content
Override it to define when two different objects are "equal". By default it behaves like ==.

    
hashCode() goes with equals
Equal objects must return the same hash code, or HashSet and HashMap break.

    
toString() for humans
Called by println and string concatenation. Default output looks like Point@1b6d3586.

  

  

  
Shortcut: a record (next chapter) generates correct equals, hashCode and toString for you.

Records

  
A record is a transparent carrier for immutable data. From the header alone, Java generates private final fields, a constructor, accessor methods (x(), not getX()), and equals, hashCode and toString.

  
  


  
Sealed hierarchies + pattern matching

  
A sealed type lists exactly which classes may extend or implement it. The compiler then knows every possible case, so a switch over it needs no default. If you add a new subtype later, every switch that forgot it stops compiling. That is a very useful safety net.

  


  
Java 25: compact source files

  
For small programs and first lessons, a file can now contain just a main method. The class around it is implicit, and IO.println prints a line. Run it directly with java Hello.java.

  

  
Java 25 Compact source files are great for learning, but real projects still use explicit classes in packages.

Cheat Sheet
The whole course on one screen. Good for revision before an exam.

  

    
Class / ObjectClass = blueprint. Object = instance made with new. Variables hold references.

    
ConstructorSame name as class, no return type. Calls super(…) first (Java 25: validation may come before).

    
this / staticthis = current object. static = one per class, shared, no this.

    
EncapsulationPrivate fields + public methods that enforce invariants.

    
AbstractionExpose a contract (interface / abstract class), hide the how.

    
Inheritanceextends, one superclass, "is-a". Everything extends Object.

    
PolymorphismReference type → what you can call. Object type → which override runs.

    
Overload vs overrideOverload: same name, different params, compile time. Override: same signature, subclass, run time.

    
Abstract class vs interfaceAbstract: state + constructors, extend one. Interface: no instance state, implement many.

    
Composition"has-a" via a field. Preferred over inheritance by default.

    
equals / hashCodeOverride both together. == compares references.

    
Records & sealedRecord = immutable data in one line. Sealed = closed hierarchy, exhaustive switch.
