1.1

The idea, in everyday life

Some things should exist only once

Think of a football match: there is one scoreboard. Every player, referee and fan looks at the same board. If each person had their own scoreboard, they would soon disagree about the score. A Singleton is a class that makes sure there is only one object of it, and gives everyone the same way to reach that object.

In one sentence: a Singleton is a class that has exactly one object, and everybody who asks for it gets that same object.

2.1
The official intent
Two promises in one pattern

  
"Ensure a class only has one instance, and provide a global point of access to it."Gamma, Helm, Johnson, Vlissides · Design Patterns (1994)

  

    
① Only one instance
The class itself prevents others from calling new: its constructor is private.

    
② Global access
A static method or field hands out that instance: Config.getInstance() or Config.INSTANCE.

    
Good uses
Something that truly exists once per program: the runtime, a hardware device, a registry, a shared cache, a stateless helper.

2.3
Lazy or eager? When is the object created?
The JVM is already lazy: a class is set up on its first use

  
Eager
The object is created as soon as the class is first used, even if nobody calls getInstance() yet.
Lazy
The object is created only on the first call to getInstance(). Useful when it is expensive and might not be needed.

3.1
Threads and the race
Two threads call getInstance() at the same time. You are the scheduler.

  
An everyday race
Two drivers see the same empty parking spot. Both think "free!", both drive in, and they crash. Checking and then acting is not one step.
The same in Java
if (instance == null) instance = new Config(); is two steps. Between them, another thread can run its own check.

4.1
Why tests hate global singletons
Shared mutable state makes test results depend on their order

  
The controversy: the pattern combines two decisions, "there is one" and "everyone can reach it". The second one is a global variable in disguise. It hides dependencies and lets tests interfere with each other. Many experts keep "one instance" and drop the global lookup: create the object once and pass it to whoever needs it.

4.2
What experts know
The details that matter in production and in interviews

  

  
A preview feature to watch: stable values JDK 25 preview

  
JEP 502 adds a preview API for values that are set at most once and then treated as constants by the JIT. It's a lazy, thread-safe alternative to the holder idiom without an extra class. You need --enable-preview to use it, and the API may still change in later releases.

  






  
4.3
Trade-offs
Convenient today, expensive later

  

    
✔ Benefits✘ Costs

    
Guarantees a single instance of something that really exists onceA global access point hides dependencies: method signatures stop telling the truth

    
Created on demand (lazy) or at class initializationTests share state and depend on their order; mocking a static call is hard

    
Can implement interfaces and be passed around, unlike a static utility classMutable singletons need synchronization; they become a contention point

    
GoF: the count can change later (e.g. a small pool) behind getInstance()"One per JVM" is really "one per class loader"; it leaks on hot redeploy

    
Saves memory for heavy, immutable resourcesBreaks the Single Responsibility Principle: the class manages its own lifecycle too

4.4
Pitfalls
Mistakes seen in real code reviews, from basic to subtle

  

    
Forgetting the private constructor
Without it, anyone can call new.✗ public Config() { }✓ private Config() { }

    
Lazy without synchronization
Check-then-act is a race.✗ if (instance == null) instance = new …✓ holder idiom or enum

    
Double-checked without volatile
Another thread may see a half-built object.✗ private static Config instance;✓ private static volatile Config instance;

    
Serializable without readResolve
Deserializing creates a copy.✗ implements Serializable (only)✓ readResolve() or enum

    
Mutable global state
Every caller can change it, at any time.✗ Settings.get().setLocale(…)✓ immutable singleton, or pass the object

    
Heavy work in the constructor
An exception there kills the class for good.✗ load files in a static initializer✓ load explicitly, report errors, allow retry

Cheat sheet
Singleton on one screen, by level

  

    
🌱 The 3 steps
Private constructor · private static final instance · public static getInstance().

    
🧭 Lazy or eager
Eager = created on class init (often lazy enough). Lazy = created on the first getInstance().

    
⚡ Default choice
enum Config { INSTANCE; … }: thread-safe, serialization-safe, reflection-safe. Need a superclass? Holder idiom.

    
⚡ Never
Lazy without synchronization, or double-checked locking without volatile.

    
👑 Know the limits
One per class loader. A failed initializer gives ExceptionInInitializerError, then NoClassDefFoundError forever.

    
👑 Better design
Keep one instance, but inject it through an interface. Tests can then use fakes.
